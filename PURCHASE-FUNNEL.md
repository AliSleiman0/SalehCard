# Customer Purchase Funnel — Assessment

Scope: the customer-facing buy flow (`/web`) and the shared Go backend (`/api`)
it depends on. Companion to [`admin/BACKLOG.md`](admin/BACKLOG.md).

**Verdict:** the funnel is a fully-built **UI prototype with zero backend behind
it past the catalog**. A customer can browse real products, but cart → checkout →
order → wallet are entirely client-side fiction: orders are fabricated in the
browser, codes are *generated by JavaScript* rather than drawn from inventory,
and nothing persists. There is **no customer authentication at all**. The Go
modules that would back this (`user`, `order`, `wallet`) exist as
fully-scaffolded interfaces (model + repo + service + handler) where **every
method returns `TODO: not implemented`**.

Legend: ✅ real · 🟡 UI built on mock/local state · ⬜ not started

## The critical missing seam: fulfillment

The supply side is **done** — admin Products + the `code` module are real: codes
are uploaded, counted, thresholded, and audited against MongoDB. But there is **no
hook that hands a code to an order**:

- `code/service.go` exposes `Upload / ListCodes / Lookup / SetThreshold /
  Inventory / LowStock` — and **no `Reserve` / `Deliver` / `Claim`**.
- The `Code` model already has the target fields (`Status`, `DeliveredTo`,
  `DeliveredAt`) and statuses (`available`, `delivered`, …), so the data shape is
  ready; the **transition logic is absent**.
- Today checkout's `genCode()` literally string-builds a code in the browser.
  Real fulfillment must atomically pick an `available` code, flip it to
  `delivered`, decrement product stock, and attach it to the order.

This seam is exactly where the finished admin supply side and the unbuilt
customer demand side are meant to meet. It's the highest-leverage single piece.

## What "focusing the funnel" actually requires

Dependency-ordered. Each step unblocks the next, and most also light up the
matching admin 🟡 screen for free (real data to render).

1. **Customer auth** — implement `user` repo+service (bcrypt, find/create),
   add public routes `POST /api/v1/auth/register|login|refresh`, `GET
   /users/me`. Issue JWT via existing `jwt.go`. Wire `LoginPage`/`RegisterPage`
   to populate the `auth` store. *Unblocks everything user-scoped; also enables
   real (non-dev-bypass) admin login.*
2. **Order placement + fulfillment** — implement `order` repo+service
   (`PlaceOrder`, `ListOrders`, `GetOrder`) and add `code.Reserve/Deliver`.
   `POST /api/v1/orders` should: validate cart server-side (re-price, check
   stock), charge payment, deliver code/credit atomically, persist the order.
   Replace `CheckoutPage.genCode()` with the real response. *Lights up admin
   Orders against real data.*
3. **Wallet** — implement `wallet` service + transactions ledger, `GET
   /wallet`, `POST /wallet/topups`. Make wallet payment in checkout a real debit.
   *Lights up admin Finance/transactions.*
4. **Order history + wallet pages** — repoint `OrdersPage`,
   `OrderDetailPage`, `WalletPage` from `lib/mock/demo.ts` to real endpoints.

Out of scope for a first cut (defer): real card/USDT gateways (keep a manual/
mock payment step), Google OAuth, saved-IDs persistence, reseller pricing.

## Risks / decisions to settle first

- **Payment for v1?** No real gateway exists. Recommend: ship with **wallet +
  a mock "card approved" path**, defer Visa/USDT. (Decision needed.)
- **Atomicity** — code delivery + stock decrement + order write should be
  transactional (Mongo multi-doc txn or a careful find-and-update on the code)
  to avoid double-selling a code under concurrency.
- **Price integrity** — cart currently trusts client-side prices; checkout must
  re-price from the DB server-side.
- **Refresh-token storage** — `api-client` expects an httpOnly refresh cookie
  (`credentials: 'include'`); the login endpoint must set it.
