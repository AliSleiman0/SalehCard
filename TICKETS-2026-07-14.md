## TICKET-1 — Dashboard: add per-status order count boxes (failed / pending / completed / refunded)

**Priority:** P2
**Type:** Task

**Description**
The admin dashboard shows 8 KPI tiles today, but none of them are a simple
per-order-status count. Add four boxes — **Failed**, **Pending**, **Completed**,
**Refunded** — so an admin can see order health at a glance without opening the
Orders list and filtering manually.

**Current state**
- Backend: `api/internal/modules/dashboard/dashboard.go`, `GET
  /api/admin/dashboard/stats` (handler `GetStats`, lines 87-188) returns a `Stats`
  struct (lines 26-46) with `revenueToday`, `ordersToday`, `activeUsers`,
  `walletTopups`, `pendingTransfers`, `pendingTopups`, `pendingKyc`,
  `lowStockCount`, `codesAvailable`, `codesDelivered` — no per-status order counts.
- Order status enum is exactly: `pending`, `processing`, `completed`, `failed`,
  `refunded` (`api/internal/modules/order/model.go:22-28`). Note "processing" is
  the queue status for account_credit/transfer orders — decide whether the
  "Pending" box means `pending` (crash-mid-placement, rare) or should read
  `processing` (the actual operator queue depth, already partially surfaced as
  `pendingTransfers`).
- Frontend: `admin/src/features/dashboard/pages/DashboardPage.tsx` renders the
  existing tiles at lines 136-207.

**Acceptance criteria**
- `Stats` struct gains 4 new counts (today or all-time — confirm with stakeholder;
  recommend "today" to match the other tiles' time window).
- 4 new KPI tiles render on the dashboard, each linking through to the Orders
  list pre-filtered to that status.
- Zero-count states render cleanly (not blank/error).

**Open question:** does "pending" in the client's ask mean the `pending` status
or the `processing` queue (which already has a tile as "Pending transfers")? Confirm
before implementing to avoid a confusing duplicate box.

## TICKET-2 — Dashboard: live polling for KPI tiles

**Priority:** P2
**Type:** Task

**Description**
Dashboard KPI tiles only load once (or on remount/refocus) — an admin has to
manually refresh the page to see updated numbers. Add polling so the boxes stay
current without user action.

**Current state**
- `admin/src/features/dashboard/hooks/useDashboard.ts`: `useDashboardStats`,
  `useLowStock`, `useRevenueChart`, `useFulfillmentBreakdown` are plain React
  Query `useQuery` calls with **no `refetchInterval`**. Only `useHealth` (lines
  24-31) polls today, at `refetchInterval: 30_000`.

**Acceptance criteria**
- `useDashboardStats` (and any other tile-feeding hooks worth it) gets a
  `refetchInterval`. Recommend **10-15s**, not literally 2s — a 2-second interval
  against a Cosmos-backed aggregation endpoint with N admins tabs open is a real
  load-multiplier for no perceptible UX gain; flag this tradeoff back to the
  client rather than implementing 2s literally.
- Polling pauses when the browser tab isn't focused (React Query's
  `refetchIntervalInBackground: false` default already does this — verify it's
  not overridden).
- No visible flicker/layout-shift on each refetch (React Query keeps stale data
  visible by default while refetching — confirm this holds).

**Note:** bundle with TICKET-1 if both are being picked up together — same file,
same hook.

## TICKET-4 — Catalog navigation: Collections → Categories → Subcategories → Products

**Priority:** P3 (scope needs to be pinned down before estimation)
**Type:** Epic

**Description (as given)**
Client's described mechanism: the app landing page shows **Collections**, each
with its own products; a separate Categories page lets a customer tap a
**Category** to reveal its **Subcategories**, and tapping a subcategory shows its
**Products**.

**Current state — this is a real, non-trivial gap**
- No "Collection" entity exists anywhere in the backend (confirmed by grep — the
  only "collection" hits are unrelated `*mongo.Collection` driver handles).
- A `category` module exists (`api/internal/modules/category/model.go`) with
  `Depth`, `ParentLegacyID`, `RootDomain` fields — the schema already supports a
  multi-level tree — **but** per its own doc comment the public API only exposes
  top-level root domains today; the parent→child drill-down isn't wired.
- `Product.CategorySlug` / `RootDomain` on the product itself is flat (one
  category per product, no subcategory reference).
- Flutter: `app/lib/features/browse/presentation/screens/categories_screen.dart`
  → `category_products_screen.dart` is a **flat** category-to-products jump today
  — no subcategory step exists.
  `app/lib/features/home/presentation/screens/home_screen.dart` shows products
  directly; there's no "collections" grouping widget on the landing page.

**Acceptance criteria (draft — needs client sign-off on the open question below
before this is buildable)**
- Landing/home screen groups products under named Collections (each collection:
  title + its product list).
- Categories page: tapping a category shows its subcategories (not products
  directly); tapping a subcategory shows that subcategory's products.
- Admin console gets CRUD for whichever new entities are introduced (collections,
  and/or subcategory assignment on products).

**Open question — resolve before scoping/estimating:** is "Collection" a
genuinely new concept (e.g. curated/seasonal groupings, distinct from category),
or is the client actually describing the *existing* root-domain categories by a
different name, and the real ask is just "finish wiring the category tree that
already exists in the schema down to a 3-level UI drill-down"? These are very
different sizes of work (new module + admin CRUD + 2 new screens, vs. extending
one existing module's API + 1 new screen). Recommend a follow-up conversation
with the client showing them the current category structure before writing
subtasks.

## TICKET-5 — Product editor: add a unit price (cost) field

**Priority:** P1 (blocks TICKET-6 and TICKET-7)
**Type:** Task

**Description**
Admins need to record a product's unit cost (distinct from the customer-facing
retail price) so inventory value can be calculated.

**Current state**
- The schema already has a home for this: `Pricing` struct
  (`api/internal/modules/product/model.go:149-156`) has `Cost`, `Retail`,
  `Margin`, `Currency` — but it's populated **only** by the legacy catalog
  importer (`UpsertProductInput`). It's completely absent from the
  admin-facing `CreateProductInput`/`UpdateProductInput` DTOs (lines 301-342),
  so there is currently no way for an admin to set it.
- `admin/src/features/products/pages/ProductEditPage.tsx` has no unit-price /
  cost field in the form.

**Acceptance criteria**
- Admin product editor gets a "Unit price" (cost) input, validated as a
  non-negative number.
- `CreateProductInput`/`UpdateProductInput` (and their handler) accept and persist
  it into `Product.Pricing.Cost`.
- Existing products without a cost set show as unset/zero, not an error.

**Technical note:** the `Pricing` struct also carries `Mode`/`ModeConfidence`
fields that look like importer migration cruft — don't expose those in the admin
form, just `Cost` (and reuse `Currency` if relevant, or assume the store's single
currency).

## TICKET-8 — Inventory: per-product codes management popup (list / add / delete / modify / status)

**Priority:** P1
**Type:** Task

**Description**
Give admins a way to see and manage the actual list of codes behind a product —
today the inventory table only shows aggregate counts. Clicking a new "Codes"
action on a product row should open a popup listing every code for that
product, its status, and let the admin add/edit/delete individual codes.

**Current state**
- Row actions today (`InventoryPage.tsx:271-289`): "Add" (opens the bulk-upload
  flow) and "Export" (CSV). **No per-row "view codes" or per-code edit/delete.**
- `Code` model (`api/internal/modules/code/model.go:24-35`): `id`, `productId`,
  `code`, `pin`, `status` (`available` / `delivered` / `expired`), `orderId`,
  `deliveredTo`, `deliveredAt`, `batch`, `createdAt`. **No explicit "duplicate"
  flag** on the document — but `BulkInsert` (`repository.go:115-161`) already
  detects and rejects duplicates at upload time (against existing DB codes and
  within the same batch), returning a `duplicates` count. So "is this code a
  duplicate" isn't a stored per-code fact today, only an upload-time check.
- Backend already has `GET /api/admin/products/{id}/codes` (paginated list,
  `routes.go:44`, gated `inventory.manage`) and `PUT /api/admin/codes/{code}/expire`
  (`routes.go:47`) — but the admin UI never calls the list endpoint for display,
  only internally for CSV export. There's no single-code create endpoint (bulk
  upload only) and no delete/edit endpoint for an individual code beyond expire.
- `api/cmd/dbtool` has `codes`/`codes-clear` CLI subcommands (masked list +
  bulk-delete, dry-run by default) — CLI-only fallback, not console-facing;
  worth knowing about but out of scope here.

**Acceptance criteria**
- New "Codes" action button per product row opens a popup/drawer listing that
  product's codes (paginated, reusing `GET /api/admin/products/{id}/codes`),
  showing code (masked or full per `inventory.manage` perm — confirm sensitivity
  policy), status (Available / Delivered / Expired), and delivered-order link if
  applicable.
- Admin can add a single code from the popup (new endpoint needed —
  single-code create, reusing the same dedup logic as bulk insert).
- Admin can delete an unused (`available`) code (new endpoint needed — block
  deleting a `delivered` code, since that would orphan the order's fulfillment
  record; offer "expire" instead for those, reusing the existing endpoint).
- Admin can edit an `available` code's value/pin (new endpoint needed; same
  dedup + not-yet-delivered constraint).
- "Duplicate" status: since it isn't stored per-code, decide whether to (a) just
  reuse the existing upload-time dedup check for the add/edit forms in this
  popup (recommended — matches current behavior, no schema change), or (b) add
  a real `isDuplicateOf` marker for audit purposes (bigger change — call out as
  a stretch goal, not required for v1).

## TICKET-9 — Code upload: strip whitespace from submitted codes

**Priority:** P2
**Type:** Bug/Task

**Description**
Codes pasted or uploaded with stray spaces (e.g. `"rer wer werer"`) should be
normalized to `"rerwerwerer"` before storage, on both bulk and single upload.

**Current state**
- Backend `code/service.go` `Upload` (lines 51-87) only checks `it.Code == ""`
  — no trimming at all. `repository.go` `BulkInsert` (lines 115-161) inserts
  `it.Code`/`it.Pin` as-is, no `strings.TrimSpace` anywhere in the write path
  (confirmed via grep).
- Frontend `admin/src/features/inventory/api/codes.ts` `parseCodesFile`
  (lines 88-102) does trim **leading/trailing** whitespace per line/field
  only — internal whitespace (spaces in the middle of a code) is never
  stripped, front or back end. Any direct API caller also bypasses even the
  client-side leading/trailing trim.

**Acceptance criteria**
- Server-side `Upload` (and whatever single-code-add endpoint TICKET-8
  introduces) strips **all** whitespace from `code` and `pin` before dedup
  check + insert — not just trim, remove internal spaces too (e.g.
  `strings.Join(strings.Fields(s), "")` or a regex strip).
- This is the authoritative fix point (server-side) since the client-side trim
  is bypassable; front-end can additionally clean on paste for UX but isn't the
  fix.
- Add a unit test: upload `"AB CD-12 34"` → stored as `"ABCD-1234"` (confirm
  with stakeholder whether hyphens/dashes inside a code should be preserved —
  presumably yes, only literal whitespace is being asked to be stripped).

## TICKET-10 — Admin: bulk push notifications to users

**Priority:** P2
**Type:** Task

**Description**
Give admins a "send push notification" action on the Users page, mirroring the
existing bulk-SMS feature (select users → compose → send), so admins can reach
users without SMS cost.

**Current state — mostly wiring, not greenfield**
- Bulk SMS reference implementation: `api/internal/modules/user/admin.go`,
  `POST /api/admin/users/bulk-sms` (route line 85, handler `bulkSMS` line 326).
  Guardrails: `maxBulkSMS` cap (default 400, `BULK_SMS_LIMIT`), 160-char
  single-segment limit (client + server), phoneless/deleted users skipped,
  detached serial fan-out, audited as `user.bulk_sms`.
- Push infra already exists: `api/internal/platform/push` has a `Sender` port
  with an FCM adapter + log adapter (mirrors the SMS `sms.Sender` pattern); the
  `notification` module (`api/internal/modules/notification/notifier.go`)
  already fans push out to every registered device token (`device_tokens`
  collection) — but currently only as a **per-user, event-triggered** side
  effect (order completed, top-up approved, etc.), never as an admin-initiated
  broadcast to an arbitrary user selection.
- Flutter already registers device tokens end-to-end
  (`app/lib/core/push/push_service.dart`, `firebase_options.dart`,
  `google-services.json` present) — client side needs no new work.

**Acceptance criteria**
- New `POST /api/admin/users/bulk-push` mirroring `bulkSMS`'s shape: selection
  → title + body → cap (reuse or mirror `BULK_SMS_MAX` pattern, e.g.
  `BULK_PUSH_MAX`) → detached fan-out via `notification.Notifier`/`push.Sender`
  → audit entry (new `user.bulk_push` action).
  Note: unlike SMS this doesn't need a per-segment character cap tied to
  carrier billing, but a sane length limit (title/body) still makes sense for
  UI/notification-tray reasons.
  Users with zero registered device tokens are silently skipped (no error),
  same spirit as phoneless users in bulk SMS.
- Users page gets a "Push" button next to the existing "SMS" button on the
  bulk-selection toolbar, with the same confirm-dialog pattern as SMS.
- No per-send cost guardrail is needed the way bulk SMS needs one (push is
  free via FCM), but keep the recipient cap for abuse/rate-limit reasons.
