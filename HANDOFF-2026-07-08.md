## The "direct" recharge model (important context)

- `alfa-direct` (8) + `mtc-direct` (7) products were imported in inconsistent half-states
  (some `code`, some `account_credit`+`manual_operator`, some `bridge_device` with
  `bridge=null`), none with a `phone` field, all with a stray `qty` field. Net: no working
  "enter the number to charge" flow (the `code` one showed no input at all).
- **Correct target** (user chose): `fulfillmentType=account_credit` + `fulfillmentMode=bridge_device`
  + `bridge={provider, method:recharge_line}` + a single `phone` input field. Provider from
  category: `alfa*`→alfa, `mtc*`→touch. `recharge_line` **consumes one uploaded scratch-card
  PIN per order** from the code pool.
- Applied to all 15 via `bridgedirect --apply` (twice — the admin editor reverted one; #60
  now prevents that). Verified `ALFA 3.03 DIRECT` = `account_credit`/`bridge_device`/`{alfa,recharge_line}`.
- Note: `transfer_credit` (the OTHER bridge method, used by the working `airtime-alfa`/
  `airtime-touch` products) needs per-variant `faceValue` and NO PINs — we did **not** use it here.

## Prod DB access + gotchas (READ before touching prod data)

- Use **`api/cmd/dbtool`** for inspection/maintenance — do NOT hand-roll scripts. Subcommands:
  `product <id>`, `codes <productId>`, `codes-clear <productId>`, `code <value>`,
  `code-clear <value>`, `order <id>`. Destructive ones are dry-run unless `--apply`
  (put `--apply` BEFORE the positional arg — Go `flag` quirk).
- **Firewall dance** (prod Cosmos `docdb-cluster-20260626-2230`, RG `salehcard-prod`): add a
  temp firewall rule for the current egress IP (drifts across `213.204.66.x`), run the tool with
  `MONGO_URI` from gitignored `DEPLOY-CREDS.local.md`, **delete the rule after**. The firewall
  PUT is **blocked in auto mode** by the classifier — must be out of auto mode.
- **TLS hang gotcha (cost ~15 min this session):** the Go mongo driver's cert verification can
  start **hanging mid-session** (`connect: timed out … total connections: 1`, ~4s) even though
  firewall + cluster are healthy. It is NOT the firewall (widening to the whole `/24` didn't help;
  a raw Python TCP+TLS test to the SRV node `fc-…-000.mongocluster.cosmos.azure.com:10260`
  succeeded). **Workaround: append `&tlsInsecure=true` to `MONGO_URI`.** Likely slow OCSP/CRL or a
  TLS-intercepting product on the box.
  Example that works:
  ```
  BASE="$(grep -oE 'mongodb\+srv://[^[:space:]]*maxIdleTimeMS=120000' DEPLOY-CREDS.local.md | head -1)"
  MONGO_URI="${BASE}&tlsInsecure=true" go run ./cmd/dbtool code <value>
  ```
